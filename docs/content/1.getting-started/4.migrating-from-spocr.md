_DRAFT_

> Use this playbook once you have audited your applications and confirmed that the remaining gaps in Xtraq have been addressed. It focuses on the final migration activity rather than discovery or optimisation.

## Overview

| Step         | Outcome                                                                                           |
| ------------ | ------------------------------------------------------------------------------------------------- |
| Prepare      | Team agrees on migration scope, timelines, and rollback plan.                                     |
| Cut-over     | SpocR artefacts are replaced with Xtraq equivalents, and cross-cutting behaviours are reattached. |
| Validate     | Regression tests, performance checks, and observability confirm parity.                           |
| Decommission | Legacy assets are retired, documentation updated, and lessons captured.                           |

## Prerequisites

- Audit of SpocR usage is complete and tracked in an internal backlog.
- Xtraq generator settings (snapshots, configuration) are verified against the target environment.
- Required features or optimisations (for example table-type trimming, execution policies, DI-scoped transaction orchestrator with ambient EF support) have landed in your branch or are covered by feature flags.
- Legacy result envelopes that must stay compatible (for example `ResponseResult`) have a documented adapter plan using pipeline policies or interceptors.
- Stakeholders sign off on the migration schedule and rollback triggers.

> 💡 **Prompt idea**: _"Review our SpocR → Xtraq readiness checklist and report any missing prerequisites."_

## Findings from legacy SpocR managers

- Managers build a shared `DbExecutionContext` (wrapping the `Context` TVP) for every call; helper methods add `RecordId`/`RowVersion`/`Overwrite` before passing inputs to the stored procedure extensions.
- Write paths wrap outputs in `ResponseResult`/`CrudResult` and call `HistoryCreateAsync` with serialized request payloads; the action/entity code is inferred from the manager/method name.
- Several workflows open explicit `SqlTransaction`s with labels and chain multiple procedures before committing (primary aggregate + related upserts, cross-entity updates, batching flows).
- Entity-change notifications rely on a `DispatchProxy` that inspects attributes (`EntityChangesDispatcher`, `DispatchEntityChanges`, `IgnoreEntityChanges`) and the request model to send `EntityChangesHubMessage`s via SignalR after successful writes.
- Many endpoints surface raw JSON from `*AsJson` procedures; downstream code sometimes deserializes that JSON again (for example payment initiation export), so raw + typed access need to co-exist.

## Recommended Xtraq extensions before migrating these managers

- Ship an ambient `Context` binder that hydrates the legacy TVP from DI/claims (user/app/language) and merges concurrency flags (`RecordId`, `RowVersion`, `Overwrite`) from request models so the generated inputs do not need manual `With(...)` plumbing. Keep the user/app/language pieces at registration time (for example via `IHttpContextAccessor`), and merge record-level data at call time via a per-procedure binding/pipeline hook.
- Provide a `ResponseResult`/history compatibility policy that maps Xtraq outputs to the existing envelopes and optionally invokes the `HistoryCreate` procedure with configurable entity/action labels and serialized payloads. Use `ResultCallbackExecutionPolicy` or `HistoryExecutionPolicy` to wrap/transform outputs without changing executor signatures.
- Add an entity-change dispatch hook (policy or interceptor) that mirrors the current proxy semantics: opt-out/opt-in attributes, parent detection on request models, and SignalR hub publishing after successful executions. The `EntityChangeDispatchExecutionPolicy` provides the hook; consumer code supplies the dispatcher.
- Extend transaction ergonomics so pipelines can attach labels and safely expose/borrow the ambient `DbTransaction`/`DbConnection` when multi-procedure flows still perform auxiliary ADO.NET work alongside Xtraq calls. `ProcedureExecutionContext` now exposes `AmbientConnection`/`AmbientTransaction` for downstream usage.

> Context-TVP Binding: Use `ParameterBindingOptions.BindTableWithInput` to merge ambient data (for example `IHttpContextAccessor` for user/app/language) with per-request record metadata at call time:
>
> ```csharp
> services.AddXtraqDbContext(options =>
> {
>   options.ParameterBindings
>     .BindTableWithInput<ContextTableType>("@Context", (input, sp, ct) =>
>     {
>       var accessor = sp?.GetService<IHttpContextAccessor>();
>       var userId = accessor?.HttpContext?.User?.FindFirstValue("sub");
>       var record = input as IRecordContext;
>       return new[]
>       {
>         new ContextTableType
>         {
>           UserId = int.TryParse(userId, out var uid) ? uid : 0,
>           RecordId = record?.RecordId,
>           RowVersion = record?.RowVersion,
>           Overwrite = record?.Overwrite
>         }
>       };
>     });
> });
> ```

## Migration Steps

1. **Generate fresh Xtraq artefacts**
   - Run the agreed snapshot/build workflow.
   - Commit or stage the generated code on a dedicated migration branch.
2. **Replace application wiring**
   - Update dependency injection and project references to point at the Xtraq assemblies.
   - Introduce the DI-scoped transaction orchestrator (or interim wrapper) so procedure calls share the intended connection/transaction scope.
   - When Entity Framework Core remains in the request pipeline, adapt your generated `IXtraqDbContext` to implement `IXtraqAmbientTransactionAccessor` so the orchestrator can join EF-managed transactions (see [Entity Framework Integration](../../3.reference/6.entity-framework-integration.md)).
   - Swap SpocR invocation sites with `ConfigureProcedure(...)`, pipeline execution methods, and policies.
   - Ensure table types, DTOs, and streaming helpers map to the new structures.
3. **Reconnect cross-cutting concerns**
   - Attach `IProcedureExecutionPolicy` implementations for retries, caching, history logging, or timeouts.
   - Register consumer-side interceptors/transformers that wrap pipeline results into legacy contracts (for example `ResponseResult`) when required.
   - Add `WithLabel(...)` annotations for telemetry and logging scopes.
   - Verify diagnostics pipelines or tracing remain functional.
4. **Feature toggles & deployment**
   - Wrap the migration behind feature flags, environment toggles, or staged rollouts.
   - Document rollback instructions referencing the flag/branch.

> 💡 **Prompt idea**: _"Refactor this service to call the Xtraq pipeline and include a labelled retry policy."_
> 💡 **Prompt idea**: _"Create a pipeline policy that maps `InvoiceCreateResult` into our existing `ResponseResult` shell."_

## Validation

- Execute automated tests covering critical stored procedures and integration paths.
- Exercise transaction rollbacks and nested transaction paths to ensure the orchestrator behaves like the legacy managers.
- Perform targeted performance benchmarks comparing latency and throughput to the SpocR baseline.
- Confirm observability signals (logs, metrics, traces) include the new pipeline labels and policies.
- Conduct manual exploratory testing for edge cases identified during the audit.

> 💡 **Prompt idea**: _"Generate a validation checklist for the Xtraq migration including performance and observability steps."_

## Decommissioning and Follow-Up

1. Toggle production traffic to Xtraq paths and monitor for the agreed soak period.
2. Remove SpocR references from solution files, CI pipelines, and deployment scripts.
3. Archive or delete legacy artefacts once rollback is no longer required.
4. Update internal and external documentation to reference the Xtraq workflow.
5. Capture lessons learned and store reusable AI prompt templates in the team knowledge base.

> 💡 **Prompt idea**: _"Draft a release note summarising the migration from SpocR to Xtraq and its operational impact."_
